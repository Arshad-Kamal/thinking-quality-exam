# Cost & Latency per Lever: Rate Cards, Token Multipliers, Serving Overhead

**2026-09-23 · Inference-time reasoning levers — effort/cost columns for the ranked lever table (pricing/latency/token-multiplier facts only; no efficacy claims)**

## TL;DR / Recommendation

**For the ranked lever table's effort/cost columns, ship these values** (analysis built on the cited facts):

1. **Thinking tokens bill as output at all three providers** — OpenAI ("reasoning tokens… are billed as output tokens"), Anthropic ("Tokens Claude uses while thinking (billed as output tokens)"), Google ("Output price (including thinking tokens)") [^2][^6][^7]. Since output is priced 3–5× input ($2/$10 GPT-6 Sol; $4/$20 Opus 5.5; $2/$12 Gemini 3.1 Pro), **anything that changes thinking volume is the dominant cost and latency multiplier**. The effort/thinking knob carries a measured spread of **up to 23× total tokens** (GPT-5 `high` vs `minimal`: 82M vs 3.5M tokens over one benchmark suite) [^10].
2. **Multi-sample levers are exactly linear in cost**: self-consistency @k = k× generations [^19]; verifier sampling scales linearly in k (measured: 2.4M→152.7M tokens as k: 2→128) [^12]; debate ≈ M×(1+R) generations plus growing peer-transcript input (M=3, R=2 ≈ 8–12× a single call, derived from the structure papers [^21][^20][^22]).
3. **Latency is output-token-dominated**: OpenAI's own heuristic — "cutting 50% of your output tokens may cut ~50% of your latency" while "cutting 50% of your prompt may only result in a 1–5% latency improvement" [^15]. So lever latency ≈ lever token multiplier (for sequential passes ≈ additive; parallel k-samples ≈ 1× wall-clock if concurrency allows).
4. **Cost mitigations worth a column of their own**: prompt caching (input reads at 0.025–0.1× of input price [^1][^3][^7]), Batch/Flex tiers (flat **0.5×** on all tokens, asynchronous/slow [^1][^3][^7]), and the reverse knob — Fast/Priority tiers at **1.8–2×** price for lower latency [^1][^3][^7].
5. **Baseline run anchor (measured, not modeled)**: Artificial Analysis reports **$1.06 per reasoning task and $2.99 per coding-agent task** for GPT-6 Sol at `max` effort (31K output tokens/task) in Sept 2026 [^11]; Anthropic's own worked example prices a cached one-hour coding session (50K in / 15K out) at **$0.525** on Claude Opus 5 [^3].

**Prompt-text levers are the cheapest row in the table**: a 200-token system block adds <1% to call cost and ~0% latency [^15], but Anthropic documents that prompt wording itself shifts thinking volume ("Please think hard before responding." vs "Answer directly without deliberating.") — so the second-order cost effect of prompt text runs through the thinking-token multiplier, not through its own token count [^6].

### 2. Thinking-token economics

- **All three providers bill thinking at the output rate** [^2][^6][^7][^8][^9]. Google is explicit that *full* thought tokens are billed even when only a summary is returned [^8][^9]; Anthropic is explicit that display settings ("summarized" vs "omitted") change nothing about billing, and summary generation itself is free [^6].
- **Thinking re-bills as input in long agent loops.** Anthropic preserves prior-turn thinking blocks in context on keep-all models and bills them as input tokens [^6]; OpenAI's GPT-5.6 family renders available earlier-turn reasoning into the next sample by default (`reasoning.context: all_turns`) and reasoning tokens "occupy space in the model's context window" [^2]. In a 40-turn coding run this compounding — not the base rate — is what makes thinking volume expensive.
- **Truncation risk is a cost, not a refund.** OpenAI: `max_output_tokens` exhaustion can mean "you could incur costs for input and reasoning tokens without receiving a visible response" [^2]. Google: hitting `max_output_tokens` while reasoning returns truncated/empty output "while still billing for any thinking tokens generated" [^8]. Anthropic's remedy guidance is either raise `max_tokens` or lower effort [^6].
- **Typical ranges** are bounded rather than published as distributions: OpenAI "few hundred to tens of thousands" + reserve ≥25K [^2]; Anthropic budget minimum 1,024, practical 16K+ for complex work, >32K flagged as long-running [^4]; Google budgets 128–32,768 (Pro) / 0–24,576 (Flash) [^8]. The only measured multi-point series I verified is Artificial Analysis: **23× between GPT-5 `high` and `minimal`** (82M vs 3.5M tokens to complete their index) [^10], and GPT-6 Sol/Luna at `max` effort consuming 31K/51K output tokens per task [^11]. Provider guidance also warns `max` effort "adds significant cost for relatively small quality gains" and "can lead to overthinking" on some tasks (Anthropic, on Opus 4.7) [^5].

### 3. Multi-sample, verifier and debate multipliers (structure + measured anchors)

- **Self-consistency**: method definition is "samples a diverse set of reasoning paths" and marginalizes [^19] — k forward passes, so generation cost is exactly k×. Input cost is k× only nominally: shared prompt prefixes bill at cached-input rates (0.025–0.1× [^1][^3][^7]), so **total cost multiplier for large-k voting ≈ k × (output-dominated share)**. The MAD review blog confirms the convention of assigning "correspondingly increased inference budget" to self-consistency when comparing scaffolds [^22].
- **Verifier pass**: one extra call = one extra (context + draft) input and one verdict output [derived]. Measured anchors: (a) deliberative ("with thinking") verification consumes **27–40× more tokens** than non-deliberative verification of the same traces [^12]; (b) verifier cost scales linearly in voting budget (2.41M tokens at k=2 → 152.7M at k=128 on GSM8K subsets) [^12]; (c) a full solve-detect-verify pipeline with 8 fast verifier samples ran at **0.80–0.96× the tokens of its unverified single-model baseline** in one paper's setup — verification cost can be partly self-financing when the pipeline truncates redundant checking [^12]; (d) practitioner survey figures (secondary): 8B-class judges ≈ $0.001/check with 76–200 ms overhead, 97% cheaper than GPT-4-class judging [^13]. That same paper documents the token-waste signature this team cares about: models "continue generating redundant checks even after reaching a solution," cued by phrases like "Wait, double-check, Let me verify" — pure billed output tokens [^12].
- **Debate**: cost scales with agents × rounds — "the escalation in the number of agents and debate rounds can drastically raise the tokens cost of debates" [^21]; "By increasing both the number of agents and the frequency of debates… this strategy results in a significant increase in token costs" [^20]. The structural count is M initial generations + M×R revisions with re-sent peer transcripts [^22] → ~M×(1+R) generations. Sparsification papers report cutting this baseline by **51.7%** (GroupDebate) and **94.5%** (S2-MAD) of tokens [^21][^20] — direct evidence that naive MAD token bills are large enough to be worth engineering around. Secondary practitioner figures: 3–5-model juries at 3–5× cost; best-of-N + judge on disagreement = "2x generation" plus judge calls on ~10–20% of requests [^13].

### 4. Latency structure

- **Output tokens dominate wall clock.** OpenAI's latency guide: generating tokens "is almost always the highest latency step… cutting 50% of your output tokens may cut ~50% of your latency," while prompt reduction yields only "1–5% latency improvement" per 50% cut [^15]. vLLM's decomposition agrees structurally: e2e = TTFT + Σ inter-token latencies, with decode steps memory-bandwidth-bound and prefill compute-bound [^16].
- **Sequential passes add linearly; parallel ones don't.** The same guide's "make fewer requests / parallelize" principles imply wall-clock ≈ max() for concurrent calls [^15]. Caveat for k-sample parallelism: OpenAI rate limits count RPM and TPM separately and bursts can return `429 slow_down` even within nominal limits (guidance: above ~1M input TPM, ramp ≤50% per 15 min) [^17] — so k=8–32 parallel samples can serialize in practice. Batch mode sidesteps sync limits entirely but at 24-hour-window latency [^1][^17].
- **Thinking raises TTFT specifically.** Gemini: at `thinking_level: high` "the model may take significantly longer to reach a first (non thinking) output token" [^8]. OpenAI offers a TTFT workaround: ask for "a short preamble before continuing with deeper reasoning" [^2].
- **Latency is purchasable in both directions.** Fast/Priority tiers cost 2×/1.8× for "significantly faster output" (Anthropic's wording) with no published multiplier [^3]; Flex halves price for "slower response times and occasional resource unavailability" (OpenAI) [^1]. No provider publishes a numeric latency SLA multiplier for these tiers — flagged as an open data gap.

### 5. Local serving (throughput-bound wall-clock; batch effects)

For a locally run model, wall-clock per agent step is ≈ TTFT + output_tokens × TPOT, with decode memory-bandwidth-bound and prefill compute-bound [^16]; the cost column becomes GPU-time, where **input and output tokens are priced identically** — removing the API's ~5× output premium that makes thinking-heavy levers so expensive remotely [^18]. Batching is the swing factor in both directions: below the saturation batch, "computing 1 vs 10 tokens can take a similar time," so k self-consistency samples submitted as one continuous batch share prefix-cached prefill and decode nearly in parallel (≈1× wall-clock at small k), while above saturation each added sequence inflates inter-token latency [^16]. Economically, effective cost is dominated by offered load, not list price: 42 vLLM runs on H100s measured **$0.21–$15.25 per M output tokens on identical hardware — a 17.5–36.3× underutilization penalty** (e.g., Mixtral 8x7B FP16: $15.25/Mtok at 1 rps vs $0.87/Mtok at 25 rps), i.e. a self-consistency sweep that keeps the GPU saturated is an order of magnitude cheaper per token than the same tokens trickled in interactively [^18].

### 6. Worked $/run arithmetic (derived, on the stated baseline)

Baseline call (`gpt-6-sol`, 2K in / 8K out incl. thinking) ≈ **$0.084** uncached-first / **$0.080** cached-repeat [^1]. Then: effort `low→high` at the measured 23× ceiling ≈ **$1.85** (though AA's `max`-effort runs landed at 31K out ≈ **$0.31/task**, $1.06/task including their whole multi-call index, and $2.99/task in a real coding-agent harness [^11]); self-consistency @5 ≈ **$0.40** ($0.20 via Batch); +1 shallow judge ≈ **+12%**, +1 full re-reasoning critic ≈ **+100%** [derived on ^12][^13]; 3-agent × 2-round debate ≈ **$0.65–0.95** [derived on ^21][^20][^22]. Cross-provider anchors: Anthropic prices a cached 1-hour Opus-5 coding session (50K in / 15K out) at **$0.525** (vs $0.705 uncached) [^3]; at `gemini-3.8-flash` promo rates the same baseline call is ≈ **$0.032** (2K×$0.75/M + 8K×$3.75/M) [^7].

## Caveats, limitations & open questions

Model prices are moving fast (AA documents a ~50% flagship price cut landing 2026-09-22 [^11]); treat every rate as a snapshot.
- **Confidence labels used above**: [measured] AA token counts and cost-per-task [^10][^11], FlexiVe token tables [^12], concurrency-aware cost sweep [^18]; [provider docs] all rate cards, billing rules, knob bounds, latency heuristics [^1]–[^9][^15][^17]; [derived arithmetic] all "×" formulas and $/run illustrations in the master table; [secondary/anecdotal] Zylos judge cost/latency figures [^13] and BenchLM's model-row mapping [^23]–^25].
- **The 23× effort multiplier is single-source and one model generation old** (GPT-5, Aug 2025 [^10]). Providers publish no per-effort token distributions; Google's `thinking_level` and Anthropic's `effort` levels have no public token-count tables beyond budget bounds [^4][^5][^8]. Blog claims of exact per-level multipliers (e.g., "high ≈ 2× none") exist but I could not verify them against primary data and excluded them.
- **Verifier-pass and debate multipliers are structural derivations** calibrated by measured anchors from math-reasoning papers (27–40× deliberative-vs-not [^12], 51.7%/94.5% MAD token reductions [^21][^20]); per-call magnitudes in a coding-agent loop will differ. Latency multipliers for parallel k-samples assume concurrency is available; OpenAI's ramp-rate limits can serialize bursts [^17].
- **Fast/Priority latency benefit is unquantified** by providers ("significantly faster" is all Anthropic publishes [^3]); likewise no public numbers for cache-hit TTFT deltas. The Claude tokenizer change (Anthropic-claimed ~30% more tokens for the same text on Claude 4.7+, per BenchLM [^24]) means cross-provider $/run comparisons should re-tokenize with the target model's tokenizer — unverified against Anthropic primary docs here.
- **Not researched by design (team boundary)**: whether any lever improves reasoning quality. Where sources bundle accuracy with cost (e.g., "0.88–0.95 accuracy at 97% cost reduction" [^13]; FlexiVe F1 columns [^12]), the accuracy figure is quoted as reported context for the cost number only.
